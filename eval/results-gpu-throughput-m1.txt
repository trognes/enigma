THE HEADLINE: the GPU loses every cell, by 1.5x to 12x.

READ THE `device` COLUMN, NOT `speedup`.  The gpu/speedup columns of this
run are wrong and flatter the GPU: the startup baseline was a -R 1 run,
and on the GPU a single climb is a whole dispatch (0.3-1.3 s here), so
the baseline subtracted startup PLUS a full dispatch.  The tell is that
the end-to-end column is FASTER than the device column in all nine cells,
which is arithmetically impossible -- end-to-end contains the device.
Fixed by subtracting the -R 1 run's own reported device time.  `device`
was always clean: the host's own timer, no startup, no host walk.

    device/cpu:  0.16 0.22 0.65 | 0.08 0.16 0.49 | 0.08 0.14 0.42

THE SHAPE SAYS THE PARALLELISM WORKS AND THE MACHINE WAS NEVER FILLED.
Time per fixture is nearly FLAT as the work grows 16x:

    L=167:  R=64 0.970 s, R=256 1.196 s, R=1024 1.288 s

64 -> 256 lanes costs 1.23x for 4x the work (one threadgroup, more lanes);
256 -> 1024 costs 1.08x for 4x (four threadgroups).  So lanes and
threadgroups are both nearly free -- what is slow is ONE LANE.  A climb
takes ~0.33 s (L=60) to ~1.3 s (L=167) on a lane against ~2-10 ms on a
CPU core: a per-lane deficit of 50-300x, which is what a long dependent
chain of gathers costs on a GPU lane against an out-of-order core at
IPC 3.32.

The GPU compensates with width, and this run gave it almost none.  A
fixture is ONE key, so threadgroups = ceil(R / lanes) = 1, 1, 4 -- and
threadgroup memory is 6912 B of 32768, so ~4 threadgroups fit per core
and the 8-core M1 holds ~32.  The run therefore used 1/32 to 4/32 of the
device.  Scaling the device column by the unused headroom predicts
2.5-6.9x over the CPU, which brackets section 12's 2-4x estimate for a
base M1 -- an EXTRAPOLATION, and the reason --keys was added: it is a
hypothesis to measure, not a result.

WHAT THIS RUN DOES NOT SHOW.  Three known handicaps, all documented as
future work rather than found here:
  - the k4 pre-pass DECODES on the GPU where the CPU takes the O(26)
    histogram path (section 2), worth 1.16-1.45x on the CPU for exactly
    this k4f10 recipe and flat in L where decoding is linear;
  - the host's per-item reporting walk is single-threaded CPU work inside
    the end-to-end column (that is the device-to-gpu gap);
  - no kernel tuning of any kind has been done, against a CPU arm
    carrying 4x-unrolled scorer loops, the histogram path, cache-resident
    uint8 tables and struct layout tuned for Apple-silicon clang.
Not measured: thermal drift (--sustained was not run), so every number
here is a BURST rate.
