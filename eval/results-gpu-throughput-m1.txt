Milestone 3, GPU throughput -- Mac mini M1 (2020), 8 GPU cores, 8 CPU cores
metal/DESIGN.md 9.  Two runs: --keys 1 (the plugboard tier) and --keys 26.

THE M1 IS THE TARGET (DESIGN.md decision 4), and this machine is the
instrument for the whole experiment ladder.  Apple silicon generally is
in scope in principle, CUDA and OpenCL later; the M2 Pro at the end of
this file is a cross-check on a second chip, not the target.

EVERY GPU FIGURE IN THIS FILE IS AT 256 LANES PER THREADGROUP, which was
the default when they were taken.  The default is now 64
(MC_LANES_DEFAULT, from the lane sweep in results-gpu-ablation-m1.txt:
1.27x at L=107), so a re-run of throughput.py on the same chip should
read about that much higher on the gpu column and nothing else.  The
speedup column's reading -- 4-6x behind the CPU -- is not changed by it.

RUN 2 IS THE MEASUREMENT.  --keys 26 --fixtures 6, -T 8 on the CPU arm:

THE HEADLINE: the GPU is 4-6x SLOWER than the same chip's CPU, at every
length and every restart count.  device and end-to-end now agree to ~1%,
so the host's reporting walk is not the issue and the startup fix holds.

RUN 1 (--keys 1) IS SUPERSEDED, NOT MERELY OLDER.  It starved BOTH arms:
one key x R restarts is too little work for either device, and moving to
26 keys lifted the GPU 2.1-20x AND the CPU 5.1-11.5x.  Its cells are not
a valid baseline for anything.

    ratio then -> now:  0.16->0.26  0.22->0.22  0.65->0.25 (L=60)
                        0.08->0.20  0.16->0.17  0.49->0.20 (L=107)
                        0.08->0.16  0.14->0.16  0.42->0.17 (L=167)

OCCUPANCY IS NOW EXCLUDED as the explanation, which is what run 2 was for.
The prediction from run 1 was 2.5-6.9x once the machine was filled.  The
GPU did gain what the prediction's mechanism said it would -- 18-20x at
-R 64, where threadgroups went 1 -> 26 -- but the ratio did not move,
because the CPU was being starved by the same fixture.  So the
extrapolation was wrong: it scaled a number that was low for a reason
that applied to both arms.

AND THE GPU IS NOW SATURATED.  16x the restarts buys 1.28-1.31x:

    L= 60:  3591 -> 4697 climbs/s     (run 1 gained 11.8x over the same step)
    L=107:  2084 -> 2665
    L=167:  1342 -> 1741

Run 1 scaled nearly linearly with R because it was far below the
machine's ceiling; run 2 is at it.  ~1700-4700 climbs/s is what an M1 GPU
does with this kernel, and more work no longer helps.

WHAT IS LEFT IS PER-LANE SPEED, AND THE GAP IS TOO BIG FOR THE HARDWARE.
Per ALU against per core, both at saturation and both 8-wide at the top
level (M1: 8 GPU cores x 128 ALUs = 1024; 8 CPU cores):

    L= 60: core 0.42 ms/climb, ALU ~218 ms  ->  ~516x
    L=107: core 0.60 ms/climb, ALU ~384 ms  ->  ~637x
    L=167: core 0.78 ms/climb, ALU ~588 ms  ->  ~754x

A GPU ALU at ~1.3 GHz with no out-of-order execution, against a core at
~3.2 GHz running this loop at IPC 3.32, should be 10-30x slower.  500-750x
is 20-50x beyond that, so something in the kernel is wrong rather than
merely narrow.

THE SUSPECT IS THREAD-MEMORY SPILLING, and it is specific enough to test.
Metal places a `thread` array in registers only if it can prove the
indexing is static; every per-lane array here is indexed DYNAMICALLY and
in the innermost loop:

  - `thread unsigned char steck[26]` (climb.metal), read twice per
    character as steck[rows[i*26 + steck[ct[i]]]];
  - `int freq[26]` in mc_components, incremented per character;
  - the climb's saved best board, same shape.

Dynamically indexed thread arrays go to thread memory, which is device
memory behind a cache -- so the decode's two lookups become dependent
memory round trips per character per toggle, which is exactly the shape
of a 20-50x excess over the clock-and-OoO expectation.

THE FIX TO TRY FIRST, before judging the design: give each lane a 26-byte
slice of THREADGROUP memory for `steck` instead of thread memory.
Threadgroup memory is on-chip.  It fits: 256 lanes x 26 B = 6.6 KB beside
the 6.9 KB of rows and ciphertext, 13.5 KB of the 32 KB budget.  `freq`
as int is 104 B x 256 = 26 KB and does not fit at 256 lanes -- it would
need `unsigned short` and/or 128 lanes, so try `steck` alone first and
read the change against these cells.

NOT MEASURED: thermal drift (--sustained was not run), so these are burst
rates.  Three known handicaps still stand and none is the explanation for
a 500x per-lane gap: the k4 pre-pass decodes on the GPU where the CPU
takes the O(26) histogram path (worth 1.16-1.45x on the CPU), the host's
reporting walk (now measured at ~1%, so negligible), and no kernel tuning
of any kind against a CPU carrying years of it.

CROSS-CHECK ON A SECOND MACHINE: MacBook Pro, M2 Pro (19 GPU cores, 8P+4E
CPU), Xcode's own Metal toolchain, same cell, -T 12 on the CPU arm:

    L      R    n   device      gpu      cpu   speedup    95% CI
  107    256    3     4100     4102    24629     0.17x  +-0.00

    same cell on the M1 mini:  2221 / 13118 = 0.169x
    on the M2 Pro:             4100 / 24629 = 0.166x

Both arms scaled by the same factor (GPU 1.85x, CPU 1.88x), so the ratio
is the same to the second decimal on two chips of two generations.  The
"chip-independent" reading in DESIGN.md 17.7 is therefore a measurement,
not an inference: a bigger GPU delivers proportionally more of the same
starvation.  The register cap reads 384 threads per threadgroup on the
M2 Pro too, so it is a property of the kernel and the compiler, not the
GPU generation.  Per GPU core the M2 Pro is slightly LOWER (216 climbs/s
against the mini's 278), which is a laptop's clocks and thermals and the
reason the mini remains the instrument for the ladder.
