SHAVING INSTRUCTIONS OFF THE QUAD-SHAPED SCORE LOOP -- MEASURED DOWN
====================================================================

The -q / -a inner loop is ~99% of a -c run, and g++ -O3 emitted 24
instructions per character for it, of which five looked free to remove.
Removing them does not buy throughput.  Recorded so the next reader does not
repeat it, and because the reason generalises.


WHAT LOOKED WASTEFUL
--------------------

  19f3: movslq %r8d,%r14          sign-extend c
  19f9: imul   $0x44a8,%rcx,%rcx  a * 17576
  1a20: movslq %r9d,%rax          sign-extend b
  1a23: imul   $0x2a4,%rax,%rax   b * 676
  1a34: movslq %r9d,%rcx          sign-extend b AGAIN, same register

Three sign extensions -- one of them twice from the same register -- purely
because decode_at() returns int while the index arithmetic is 64-bit.  And the
4-D index rebuilt from scratch every character, although consecutive windows
(a,b,c,d) -> (b,c,d,e) share three letters.


THE VARIANTS, AND WHY NONE OF THEM IS FREE
------------------------------------------

  variant                        insns  imul  movslq  loop-carried chain
  original, int                     24     2       3  none
  unsigned, Horner index            21     3       0  none
  unsigned, flat index              21     3       0  none
  unsigned + rolling context        19     2       0  imul -> sub -> imul

Two things cancel the paper gain.

**unsigned costs an imul.**  With int, g++ sign-extends and then reaches x*26
through LEAs; with unsigned it stays in 32-bit and emits imul instead.  So
removing three movslq buys one imul.  A wash, in two different spellings of
the index -- Horner and flat give identical code.

**The rolling context creates a dependency that did not exist.**  Carrying
ctx is the only variant that reaches 19 instructions, and it is also the only
one where each iteration's index depends on the previous one: ctx --imul-->
idx --sub--> ctx', about 4 cycles of loop-carried latency.  The original
computes each index from three independently available letters, so its
iterations are fully independent and out-of-order execution overlaps them.
Fewer instructions, longer critical path.

Note the trap inside the trap: the obvious rolling update
(ctx - a*asize^2)*asize + d costs two multiplies and leaves THREE imul in the
loop, one MORE than rebuilding the index outright.  Taking the next context
from the index instead -- idx = a*asize^3 + next -- gets back to two.  That is
the difference between a 21-instruction loop and a 19-instruction one.


THE MEASUREMENT
---------------

make bench LONG=1 BASE=origin/dev, g++, rolling-context variant, with a
base-vs-base control of origin/dev against itself on the same box:

  tier         A/B quick   A/B long   control quick   control long
  search           -0.9%      -0.6%           -3.0%          -0.6%
  hillclimb        +8.2%      +4.9%           +0.9%          -2.3%
  fused            +6.7%      -8.7%           -5.8%          +1.1%
  crib             +0.6%      -0.2%           +0.9%          -0.1%

**Only hillclimb measures the change, and it reads as a REGRESSION** -- both
tiers positive, the long one above its own control.  Nothing here is a win.

Byte-identity of the change itself was verified rather than assumed (123 cells
over ten schedules x six climb-option combinations x -T {1,4}, plus Norway,
M4, the plain scan, -F, --ring-stride, --confidence, --exhaust, --soft-plug
and ENIGMA_HIST; 0 differing; suite 632/632).  So the regression is a
throughput effect, not a behaviour change.


TWO ERRORS WORTH MORE THAN THE RESULT
-------------------------------------

**-f DOES NOT USE THE FUNCTION THAT WAS CHANGED.**  The fused path goes
through ngram_ic_decode(), which takes the table as a parameter and
accumulates the IC histogram in the same pass; quadgram_score_decode() and
allgram_score_decode() serve -q and -a.  Disassembling score_iter() shows
three quad-shaped loops, and it is easy to see "both quad loops changed" and
assume -f is covered.  It is not: the third loop, 25 instructions with the
extra freq[d]++, is the one the recommended recipe actually runs.  So this
work optimised the two models the recommendation does not use.

**That accident produced a free noise control, and it is the sharpest number
in the run.**  Because the fused tier's code was byte-identical across the
A/B, its **-8.7% on the long tier is pure measurement noise** -- on a tier
whose own base-vs-base control read +1.1% in the very next run.  Two
independent estimates of the same floor, 10 points apart.  That is the
CLAUDE.md warning in its strongest observed form: a container's bias is stable
within a session, so repeating a number does not make it real, and only a
different instrument settles anything under ~10% on this tier.


WHAT THIS SAYS FOR NEXT TIME
----------------------------

The loop is **not front-end bound**.  Instruction count fell 24 -> 19, a 21%
reduction, and throughput did not improve on any tier that measures it.  So
the binding constraint is elsewhere -- most plausibly the six loads per
character against two load ports (~3 cycles/iteration), or the four-deep
dependent load chain ct -> steck -> rows -> steck.

**Stop shaving instructions here.**  The remaining lever on this loop is
reducing LOAD COUNT, and there is one candidate: rows[] is an array of 8-byte
pointers, and within a run where only the right wheel steps rows[i+1] ==
rows[i] + 26, so a run-structured scorer could advance the row by addition
instead of loading a pointer -- one fewer load of six.  setup_mapping()
already computes those runs (notch_gap).  Note this is NOT the measured-down
"2-byte row index instead of the 8-byte pointer" (+26%, archived/
IMPROVEMENTS.md §4), which changed the storage rather than removing the load.

Reproduce: the three variants are one edit each to quadgram_score_decode()
and allgram_score_decode() in src/scoring.cc; count with
  objdump -dC --no-show-raw-insn src/scoring.o | sed -n '/score_iter/,$p'
and look for the backward jne loops containing movzbl.


THE FOLLOW-UP: REDUCING LOAD COUNT -- REAL, BUT ON THE WRONG MODEL
==================================================================

The prediction above was that load count, not instruction count, is the
binding constraint.  Tested by removing one of the six loads.

**The change.**  setup_mapping(m, true) copies every row into the contiguous
mapping[] and points rows[i] at it, so on the HILL-CLIMB path
rows[i] == &m.mapping[i][0] and the row address advances by a constant asize.
Walking it (row += asize) instead of loading an 8-byte pointer takes the loop
from six loads per character to five.  The SCAN path points rows[] into
subst_array with no such stride and keeps the indexed form.

Applied to quadgram_score_decode (-q) and ngram_ic_decode (-f).  Note the
second one: the earlier attempt changed -q and -a and missed -f entirely.

  loop                        insns  loads  8-byte ptr loads
  indexed (scan, unchanged)      24      6                 1
  contiguous (climb)             24      5                 0

**The measurement has its control built in.**  search and crib run without -c,
so they take the indexed branch and execute byte-identical code -- their
movement in the same run IS that run's floor, measured simultaneously rather
than in a separate job on a box in a different state.  That is the flaw in the
instruction-shaving A/B above, where fused read -8.7% and its own control read
+1.1% thirteen minutes later.

  tier         g++ treat   g++ floor   clang treat   clang floor
  hillclimb q      -7.3%        0.9%         +5.1%         3.4%
  hillclimb l      -6.6%        2.3%         +3.2%         0.6%
  fused q          -6.0%        5.8%         +2.6%         1.0%
  fused l          -4.2%        1.1%         -3.4%         1.8%
  search/crib   +0.3..+4.1  (controls)   -0.1..+2.0   (controls)

**g++: a clear win.**  All four treatment cells negative; hillclimb clears its
floor by ~3x on both tiers.

**clang: a small regression on hillclimb** (+3..+5% against a tight floor),
fused ambiguous (-3.4 long, +2.6 quick, both near the floor).  Clang still
loads the pointer in the indexed form -- verified by disassembly, ptrloads=1
per character -- so it is not that the change is redundant there; clang simply
does not convert the saved load, and it unrolls these loops 2x where g++ does
not, which may be where the difference lives.

**Absolute times are what make this shippable.**  hillclimb long is
g++ 15.04 -> 14.04 s and clang 12.21 -> 12.60 s.  Clang was ~20% faster before
and remains faster after; the change narrows the gap, handing most of a 7% gain
to the slower, default compiler for ~3% off the faster one.  Both are far
inside the 10% CI report and 25% block thresholds.

**So the headline finding stands and is now two-sided**: instruction count is
not the constraint (21% fewer bought 0%), load count partly is (17% fewer buys
5-7% under g++), and the remainder is presumably the four-deep dependent chain
ct -> steck -> rows -> steck, which no reordering removes.

Byte-identity: 135 cells (120 climb over eleven schedules x five climb-option
combinations x -T {1,4}, plus 15 covering Norway, M4, plain scan under -q/-f/-a,
-F, --ring-stride, --confidence, --exhaust, --soft-plug and -A), 0 differing,
plus a short-text guard at L = 1..7.  Suite 632/632.


ISOLATING THE -f PATH KILLS IT: THE GAIN WAS NEVER THERE
--------------------------------------------------------

The split above -- g++ +7% and clang -3..5% on hillclimb -- has a mechanism,
and the mechanism suggested a fix: apply the walk only where it wins on BOTH
compilers, which the disassembly said was ngram_ic_decode (-f).

**WHY THE SPLIT HAPPENS.**  clang unrolls the quadgram loops 2x and leaves
ngram_ic_decode rolled.  Walking the row needs TWO induction variables (i for
ct[i], plus the row pointer) where the indexed form needs one, so under
unrolling the added increment costs more than the removed load:

  loop (per character)      clang insns  clang loads  unrolled
  quadgram indexed                 18.5            6  2x
  quadgram contiguous              20.0            5  2x
  ngram_ic indexed                 24              6  no
  ngram_ic contiguous              24              5  no

Rolled, instruction count is identical and the saved load is pure gain; that
is why -q regressed under clang and -f did not.

**BUT ISOLATING -f SHOWS THE -f GAIN WAS NOISE.**  The -f code is IDENTICAL in
the two variants, so these four cells measure one thing twice:

  fused tier            g++ quick  g++ long  clang quick  clang long
  inside full change        -6.0%     -4.2%        +2.6%       -3.4%
  ISOLATED (-f only)        +1.4%     -1.7%        +1.8%       +2.0%

The isolated run carries three control tiers (search, hillclimb, crib -- all
now unchanged code) reading -2.0%..+1.4%, so it is the trustworthy one, and it
says the -f path gains NOTHING.  The earlier fused improvements were noise
riding alongside the real effect in the neighbouring function.

**WHAT ACTUALLY EXISTS**, therefore:

  - a real ~7% g++ win on hillclimb (-q), reproduced on both tiers against
    in-run controls;
  - a real ~3-5% clang loss on the same;
  - nothing measurable on -f, under either compiler.

**SO IT IS NOT WORTH SHIPPING.**  -q is not the recommended model.  The change
optimises a model nobody is told to use, in opposite directions on the two
compilers, and does nothing for the one that matters.  Code reverted; the
finding kept.

**A refinement of the headline worth carrying.**  Removing a load pays in
quadgram (pure gather loop) and not in ngram_ic_decode (same loop plus a
freq[d]++ store per character).  So "the loop is load-bound" is too coarse:
the quad loop is, and adding one store per character is enough to change the
balance.  Any future attempt should measure the two separately rather than
assuming what helps one helps the other.

**One measurement caveat on all of the above.**  The box drifted ~7% across
the session -- hillclimb long base ran 15.04, 16.06 and 13.23 s in different
runs -- so only within-run treatment-versus-control contrasts are meaningful
here, and no cross-run comparison in this file should be read as a difference
between variants.
